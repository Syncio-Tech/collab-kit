# conversation/

A spec ↔ implementation channel between two parties and their agents, managed by
[collabkit](https://github.com/Syncio-Tech/collab-kit). Read this at the start of every session.

<!-- collabkit:start -->
## Parties

| role | agent | human | mode |
| --- | --- | --- | --- |
| spec-owner | `{{spec_agent}}` | `{{spec_human}}` | `{{spec_mode}}` |
| implementer | `{{impl_agent}}` | `{{impl_human}}` | `{{impl_mode}}` |

Source of truth: `config.yml`.

## Layout

```
conversation/
  README.md        this file (spec-owner only)
  config.yml       parties, modes, limits (spec-owner only)
  INDEX.md         generated by `collab index`
  _templates/
  SYNC-001/
    ticket.md      frontmatter + problem statement (written once by the opener)
    01-<id>.md     one file per turn; never edit another party's turn
    99-conclusion.md
```

## One round

1. **human** `collab sync` - spec repo on the default branch, up to date.
2. **agent** `collab` - what waits for you, as numbered steps. Do them, then `collab check`.
3. **human** `collab ship` - branch, commit, push, PR link. (An `agent_push` agent may ship itself.)
4. **human** merge the PR on GitHub. Back to 1.

Nobody pushes to `main`. Ticket ids can be short: `4` = `SYNC-004`.

## Levels

| level | meaning | who decides |
| --- | --- | --- |
| T0 | no product change: wording, docs, naming | implementer or spec-owner human |
| T1 | make code match the spec, or a change proven not to alter results | implementer human |
| T2 | changes results or shape; differs from spec; new feature; touches a signed document | spec-owner human |
| T3 | a shipped product is producing wrong results on real data | spec-owner human, now |

## Rules

1. The opener sets the level and a one-line reason (`level_reason`).
2. An agent may only **raise** a level. Lowering needs a human (`level_override_by`).
3. At most `max_turns_per_point` turns per point per agent, `max_turns_per_ticket` turns and
   `max_points_per_ticket` points per ticket. Still disagreeing → T2, and the options go into the conclusion.
   A new topic is a new ticket, not a new point.
4a. When the other side agrees on every point, do not reply: `collab conclude`, write it, `collab sign`.
4b. A signature covers the conclusion text. Changing the text after someone signed voids their signature.
4c. A spec change is always decided by the spec owner's human, whatever the level.
4. Any ticket saying the code differs from the spec is T2 or higher.
5. Every ticket points to an original requirement. None → `requirement: NO_REQUIREMENT`, state `parked`.
6. Do not concede to close faster: open disagreements become options for the human, with trade-offs.
7. A conversation PR touches only `conversation/`. A spec change is a separate PR, after approval.
8. No secrets, credentials or customer data in the conversation.
9. At most `max_new_tickets_per_week` new tickets per agent per week, except T3.

## Spec-side team (optional)

When `parties.spec-owner.members` lists specialists, the spec side is a team: one owner, one or more specialists,
each with an agent and a GitHub login.
- A ticket the implementer opens waits on the owner's agent until the owner assigns it: `collab assign <id> <agent>`.
- The assignee works it with the implementer. Turn and point caps count per side, not per agent.
- A point only the owner can decide: `collab escalate <id> --note "..."`; the owner answers with `collab resolve`.
- Both sides sign; then the level's approver decides (`approve` in config: by default T0/T1 a specialist may, T2/T3 the owner).
  The owner may send an agreed conclusion back: `collab decide <id> --decision return --note "..."` (signatures void).
- A spec change needs an approval by a spec-side human allowed for that level.

## States

`open` → `discussing` → `agreed` (conclusion signed by both agents) → `approved` (human decision)
→ `in-spec` (spec PR merged + tagged) → `conformed` (code matches that tag).
Side exits: `parked` (not now) · `rejected` (no, with reason).
T0/T1 that only change the implementer's code: `agreed` → `conformed`.
